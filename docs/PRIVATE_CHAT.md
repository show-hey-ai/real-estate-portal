Property detail pages and listing-card chat buttons open `/chats?listing=<id>&start=1`. Confirmed members can start one buyer–seller conversation per property and connected seller. Sellers open their inbox for that property. `/chats` lists only conversations in which the current Supabase authentication subject participates. A room address is not an access credential.

New rooms use an explicitly connected seller when present; otherwise they connect to the configured Ziyou management desk. The desk is pinned to an immutable Supabase subject in the private `property_chat_operator` table. Setup verified a single registered, email-confirmed, active administrator; new starts recheck that this designated operator remains active and authorized. Newly added administrators never automatically inherit the desk or access to its rooms. Management sees its participating rooms at `/admin/chats`; `/chats` works for both sides. Listing review shows the connected management desk and permits an optional, authorized property-specific seller connection. REINS contact data and the uploader are never inferred as seller identities. Changing a seller or desk affects future rooms; existing rooms retain their original participants.

The chat includes viewing requests (preferred date/time and notes) and purchase requests (JPY amount and notes). These are saved as structured events, with originals in the selected message language. Requests automatically advance initial progress to viewing arrangements or purchase negotiation. Only the assigned counterpart may record contract, settlement/handover, completion or withdrawal progress; the buyer cannot mark the transaction complete. Every progress update is retained in the message history and retries cannot alter a previously recorded event. Forms lock while sending to preserve drafts. This is a transaction communication and progress workspace: it does not execute electronic signatures, payments, title transfers or legally conclude a sale.

Room and message reads require the immutable authenticated Supabase subject on the server. There is no administrator bypass for reading conversation content. Database row-level policies allow authenticated readers to see only their own rooms and messages, and deny browser writes and access to seller assignments. All writes use guarded server routes. Mutation requests require a matching Origin; message fields, language, length and nonce are validated. The database serializes message sends per room, deduplicates retries, and limits each participant to 20 new messages per minute per room. Chats use no-store responses and noindex metadata and do not mount the public analytics tracker. This is participant access control, not end-to-end encryption against infrastructure operators.

Automatic translation uses the browser's built-in Translator API, after the user enables it to authorize any language-model downloads. This requires a supported desktop browser; unsupported browsers and unsupported language pairs display the original text with an explicit notice. Japanese, English, Simplified Chinese and Traditional Chinese are supported in the interface, with `zh` and `zh-Hant` used for the browser API. Translation instances are discarded when the viewing language or room changes. Original message text and its selected source language are retained; translated text is generated on the viewing device and is not sent to an external translation provider or stored as the original. No paid AI API is invoked, preserving the zero-yen AI budget.
